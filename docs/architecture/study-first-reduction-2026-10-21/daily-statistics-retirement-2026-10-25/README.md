Both implementations first check configured-provider watermarks against the next date and then missing game features (excluding adaptive-excluded or failed-analysis games from the block list). `waiting-sync` takes precedence over `waiting-analysis`. Eligible-game selection uses `substr(played_at,1,10)` while aggregation uses stored feature `local_day`; this is existing behavior, not a timezone redesign in this packet. Deterministic IDs and insert-ignore preserve the original insight evidence on conflict.

**A completed daily job can contain a waiting snapshot.** The legacy executor ignores the refresh payload's status before marking the job complete; the PostgreSQL executor also completes the job/task after storing a waiting snapshot. Neither automatically requeues that day upon readiness. This distinction must survive readback and any retirement receipt. No claim is made that this is a new defect or fixed here.

## Proposed acceptance contract: stop admission, settle issued work, retain facts

This is the concrete next implementation contract for review, **not an implemented switch or authorization to touch live state**. Keep the present runtime unchanged until its prerequisites are supplied. The conservative policy is drain accepted work through its existing owners; no blanket cancellation, setting toggle, status rewrite or inference of an empty queue is accepted.

1. **Freeze the closure identity and first-issuance boundary.** An authorized owner supplies the actual target/version and cutoff plus the exact pre-cutoff command/broker/client obligation set. New first-time refreshes must receive an explicit retired response before any broker send, job upsert or task generation. Existing operation IDs retain digest conflicts, saved terminal response/error, pending status and matching-envelope recovery. A bare route deletion or handler unregister is insufficient. A broker-accepted command with no receipt yet, or a saved client envelope with uncertain delivery, is unresolved accepted work until reconciled; absence from `operation_receipts` is not permission to reject it as new. No new generic gateway or outbox is proposed.
2. **Retain execution and recovery until obligations settle.** Keep command registration, existing receipt/operation status and retry APIs, task handler/kind admission, legacy claim/execute and relevant controls while any accepted work remains. Reconcile `operation_receipts` for `statistics.daily.refresh` (including `pending`, `queued`, `executing`, `retrying`, `blocked`); `background_tasks` for kind `daily_statistics` (including generation, token/lease, queued/leased/retrying/failed/superseded history); `daily_statistics_jobs` (queued/running/failed); matching `background_activity` sources `statistics` and `durable`; broker reserved/in-flight/redeliverable commands and external client envelopes. These are separate authorities, not counts to add. A complete admission receipt with a queued job is unsettled materialization. A failed/blocked item keeps its error and requires an explicit owner disposition; paused or abandoned-running work is never silently completed. Do not enable optional processing or change Study-only mode to force drainage.
3. **Accept the final stored results with their actual status.** Drain under existing readiness/lease/transaction rules. A waiting snapshot may be retained as waiting after its job finishes; the owner must explicitly accept that terminal materialization attempt or keep the refresh path for a same-day retry. A newer same-day task generation fences an older delivery. Settling command admission alone is insufficient. Keep all resulting insight evidence and error/receipt history.
4. **Freeze historical facts at the coordinated boundary.** Before withdrawing recomputation, review the exact sync invalidation call sites above with their owner. Preserve the final snapshots/insights byte-for-byte, version/status/timestamps and export/read access, and retain the pending-work inventory separately. Preserve later game imports and feature derivation. Do not claim preserved historical reports are current recomputations. The existing export/checksum plus an explicitly scoped pending-work receipt can be evidence; neither has been collected here.
5. **Only then approve an exact source-removal manifest.** The reviewer supplies allowed paths/function/wiring edits, retained replay/history interfaces and source-absence checks at the assembled head (preserving merged PR426's exclusions). Keep compatibility execution if any old delivery can still arrive. Gate closure requires an authorized statement backed by the settled inventory and retained unknown-delivery policy, not an arbitrary quiet interval or grep result. Tables, stored history, queue admission and downstream priority semantics remain outside deletion authority.

If actual obligations cannot be established without forbidden access, this task stops at documentation. That is the present status. The missing input is the owner-reviewed target/cutoff and obligation/settlement/history disposition; it is **not** a request to inspect live Study or guess zero pending rows.
