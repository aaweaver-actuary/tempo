# Engine selection fairness

PR #123 reconstructs the fairness feature from `72c64edc` on current main `8fff21ac` (classification C). Its historical shared infrastructure is superseded; admission, Redis fencing, receipts, task identity, worker lifecycle and CI remain current. Migration 045 adds a singleton `engine_scheduling_state` row. Migration 043's `background_scheduling_turns` continues to govern durable tasks separately. Published migrations are unchanged.

An eligible interactive exercise attempt has priority and leaves the engine streak unchanged. Accepted defensive validation and recommendation leases, including manual promotions, increment the streak atomically with the lease and receipt, capped at three. At three, an available eligible ordinary game causes the automated claim to yield with an optional `preferred_game_id`. Without an available ordinary game, automated work continues and the streak stays three. Accepted ordinary search/finalization leases and committed terminal-position progress reset it. A later failure or release does not undo an accepted selection. Empty, rejected, stale and rolled-back claims do not spend a turn.

The bound is three accepted automated selections before an ordinary opportunity, assuming ordinary work remains eligible and available and interactive demand is finite. It is not a time or CPU-share guarantee. Pauses, rating/speed filters, generations, existing leases and priority ordering still apply. Interactive work can delay ordinary service. A hint reserves no lease: the next cycle rechecks eligibility if preparation or acceptance finds it stale.

PostgreSQL discretionary selections first lock the singleton with `SKIP LOCKED`, then acquire request/game locks. Interactive selections bypass the singleton. Ordinary eligibility uses the existing indexed job predicates and skips locked job/game candidates. Hinted chess traversal runs outside the write transaction. Acceptance rechecks generation, pause, position and leases; rejected writes roll back without changing fairness debt. Existing receipts recover before preparation and new ordinary claims check interactive eligibility. The existing 25 ms lock and 250 ms transaction budgets are unchanged. SQLite uses the same scheduling helper within its compatibility transaction.

## Evidence and boundaries

`backend/tests/test_engine_fairness.py` provides separately named compatibility/API regressions. `scripts/check_postgres_engine_fairness.py` runs in the regular durability background-workload scenario using an owned fixture database and admission namespace. It exercises production position preparation/claims, actual receipts, process restart/crash, deterministic concurrent transactions, foreground/turn contention, rejected writes, terminal/finalization selection and a normal-driver 44-to-45 upgrade followed by repeated application. The mixed-backlog proof validates actual synthetic engine reports, records per-class completions and oldest eligible age, and retains JSON query plans for 3,000 ordinary jobs and 3,000 ineligible automated requests. Search, evaluation, preemption, repair cadence and resource allocation are outside this change.

Related work: #43 requests engine fairness; #39 retains admission requirements; #42 retains maintenance/repair-loop requirements; #44 retains preemption requirements. This reconstruction does not complete those separate requirements or alter PRs #124–#131. CI owns complete candidate qualification; focused development evidence is not release or merge qualification.
