# Position-claim diagnostics

Set `TEMPO_POSITION_CLAIM_DIAGNOSTICS=1` before starting the API, background command worker and engine worker in an isolated diagnostic environment. Restart those processes when changing the flag so pooled connections use the diagnostic cursor. The default is disabled. No diagnostic endpoint or receipt migration is introduced.

Each delivery emits an operation digest (the first 24 hexadecimal characters of SHA-256 over its existing journal identity). The API, command worker and engine journal use the same digest across retries and restarts. Raw operation IDs, payloads, SQL text/parameters, user records, credentials, lease tokens and exception messages are excluded. Worker ownership uses a digest of its attempt token, plus the attempt number. Treat these records as private operational evidence; retain them locally and publish only sanitized disposable-fixture findings.

API/worker traces contain at most 96 events with an omitted-event count. Fixed labels distinguish database admission, connection acquisition (including failure before a connection exists), configured transaction/lock budgets, statement families, handler work and commit/rollback cleanup. Connection acquisition records the PostgreSQL backend PID once available. Receipt lookup, preparation and dispatch spans connect these reservations with HTTP handling; receipt observation records only its fixed state. Engine delivery records complete, retained-for-retry or terminal-failure outcomes. Durations are nested measurements and must not be added as independent elapsed time.

Events remain buffered during reservations and are emitted after the owning scope releases its database connections and admission leases. Diagnostic sink failure preserves the result or original exception. The flag does not increase timeouts, run engine searches, change scheduling, or inspect blockers through additional SQL inside a reservation. To establish lock ownership, query `pg_stat_activity`, `pg_locks` and `pg_blocking_pids` separately in the disposable environment and correlate the backend PID locally.

A position claim that encounters `TransactionTimeout`, `LockNotAvailable` or `PoolTimeout` while observing receipts or preparing/dispatching a claim returns HTTP 503 with `Retry-After: 1` and instructs the caller to retain its Idempotency-Key. The journal retains unresolved operations and recovers the same request before claiming fresh work. Completed replay, pending 202 attachment, 409 identity conflicts and terminal receipt failures retain their established semantics. Other SQL failures remain errors, rather than an empty successful claim.

The synthetic PostgreSQL regressions prove the transient HTTP classification and recovery behavior. They do not identify why the historical candidate read exceeded its transaction budget. Reproducing that cause requires a matching operation digest, stage timings, configured budgets, backend ownership/blockers and receipt/attempt state from the same request.
