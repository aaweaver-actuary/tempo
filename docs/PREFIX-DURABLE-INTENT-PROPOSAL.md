# Durable prefix intent reservation and discovery

## Proposed outcome

Related: [issue 81](https://github.com/aaweaver-actuary/tempo/issues/81), [roadmap 76](https://github.com/aaweaver-actuary/tempo/issues/76), [PR 187](https://github.com/aaweaver-actuary/tempo/pull/187). This is a protocol proposal for separate implementation, reviewed alongside structural admission. It does not implement or qualify server reservation. Today's browser-only reservation supplies no cross-device pre-admission fence.

After a server accepts an approved prefix intent, deleting every browser journal and reloading must rediscover the same logical application, restore its approved request and affected scope, preserve conflicting structural edit protection, and recover through its existing operation receipt. No apply delivery may precede that durable acceptance. Completion still requires matching graph, integrity and daily queue publication.

Approval that disappears before the server has persisted it cannot be reconstructed. Under the new protocol it has not permitted apply delivery. A lost reservation acknowledgment is ambiguous: reload discovers the reserved intent before enabling confirmation or structural controls. Repeating reservation must converge even if its first request reaches the writer later.

## Minimal extension to the existing prefix workflow

Use the existing command gateway, foreground writer, operation receipts, application records, reservation barrier, structural fences and sliced publication workers. Add a prefix reservation phase, a small immutable approval-to-operation association and a repertoire-scoped recovery read. Do not build a second generic operation subsystem or give the deployed HTTP API writer credentials.

The reservation HTTP route dispatches a new prefix-specific reservation command to the existing foreground writer. Its short writer transaction creates or returns the canonical application identity, persists the complete immutable apply envelope and validated plan/scope, creates a `reserved` application, and installs the existing card and repertoire fences atomically. Preparation and plan computation occur outside that transaction; locked revalidation closes the read/write race. Reservation does not create staging work, mutate depths/cards/history, or authorize publication.

Keep reservation transport command receipts separate from the one logical apply identity. A broker acknowledgment is not durable reservation acceptance. The browser proceeds only after a matching committed reservation response/status or authoritative discovery establishes the canonical apply identity and saved approval. Transport refusal or deadline expiry retains an actionable reservation-uncertain state and starts with discovery next time.

Extend `prefix_transition_applications` with `reserved` and a durable approval identity association. Save the exact apply payload in its existing `operation_receipts.payload_json`, under command `repertoire.prefix_transition.apply`; represent its undispatched phase explicitly in the prefix application/status, rather than making a generic queued receipt eligible for automatic execution. The reservation transport receipt and apply receipt are committed consistently. Existing `pending` receipt semantics need explicit qualification with the reservation phase.

The application generation, approved plan JSON, target repertoire and affected card/repertoire sets are persisted, including absent replacement identities. Reservation fences must be enforceable against every existing structural writer immediately. Update the fence-owner predicate deliberately: only the validated reservation/apply/release code may use a reserved owner bypass. Inspection and ordinary reviews retain their existing access; reviews may still invalidate the saved plan before activation.

## Proposed interfaces and identity rule

- `POST /api/repertoires/{id}/prefix-transition/reservations`: accepts the existing approved apply-request fields, optional explicit `renewal_of_operation_id`, and reservation transport Idempotency-Key. Returns a committed canonical apply operation ID, immutable saved request, validated scope/summary, reservation phase and status URL. A 202 that only acknowledges transport never grants permission to apply.
- `GET /api/repertoires/{id}/prefix-transition/operations`: discovers unresolved operations affecting this repertoire, including operations targeting another repertoire that fence shared scope. Includes reserved, queued, executing, retrying, staging, staged, publishing and blocked/recovery-required records; returns unresolved records first, at most 50 most recent terminal records with a cursor, and supports exact approval/predecessor lookup independent of age. Approval associations and cancellation tombstones are retained for the workspace lifetime so delayed deliveries cannot recreate them. Reads must be authoritative on the primary using read-only credentials. Service failure and unsupported storage are explicit; an omitted task from diagnostics is not authoritative absence.
- Extend operation status for prefix operations with the immutable request, trusted target/affected scope and reserved phase. Existing GET status, same-ID apply and blocked retry remain the recovery controls. The browser verifies identity and publication exactly as before.
- Add an explicit release command limited to a reserved, never-dispatched intent. It serializes with first apply admission, leaves a durable cancellation tombstone, and removes fences atomically. It cannot cancel staging, activation or publishing. Browser inactivity or storage deletion never releases reservations.

Canonical identity is bound to the current workspace database (no new tenant identifier in this single-workspace model), repertoire, exact reviewed plan identity and normalized immutable request, excluding delivery-specific UUIDs. Concurrent or delayed reservations of that same approved plan return its original apply identity and result/tombstone, including after completion; they never allocate a second logical application. A different request cannot reuse that approval identity. Distinct overlapping approvals receive an actionable conflict identifying the existing operation; disjoint scope remains eligible.

A fresh legitimate transition normally uses a newly reviewed authoritative plan after relevant state changes. For an unchanged cancelled/rejected plan, Renew approval is a separate explicit user action after re-review. Its reservation request includes `renewal_of_operation_id` naming that terminal predecessor. A small prefix approval association with a unique key on repertoire, plan ID and predecessor (empty for the original approval) stores the canonical successor and normalized request digest. The writer verifies the predecessor is cancelled/rejected before activation, revalidates the newly reviewed request and atomically creates or returns one successor. Lost renewal acknowledgments and repeated requests with different transport keys return that successor. A delayed original reservation still resolves its original tombstone; it cannot create a successor. Renewing an activated/complete operation is refused; a later structural change needs a fresh plan. Retain every predecessor and tombstone; silently minting a UUID is insufficient. Do not use a perpetual hash of desired depths: it would conflate distinct future user decisions.

## Browser behavior

On initial workspace/repertoire load and before another confirmation, perform recovery discovery. Until it succeeds, conflicting structural actions remain disabled with useful status; training and inspection continue through their existing independent paths. Discovery failure cannot enable controls. In a mounted tab, preserve unresolved in-memory identity if local storage disappears; after reload use server evidence. Treat a missing local record as a cache miss.

After confirmation: reserve durably, bind the returned canonical operation, then deliver apply with that identity. On interrupted reservation: discover before another reservation. On interrupted apply: read existing status before any same-ID delivery or explicit blocked retry. Rebuild the journal from the server request/scope without inventing plan values, and support recovery if local writes continue failing. Reserved recovery offers Continue approved transition and Release reservation; it does not auto-apply on mere page opening.

The apply boundary atomically admits a reserved operation and makes it eligible for the existing durable execution/recovery path. It revalidates the original approval; stale inputs produce explicit rejection and release preactivation fences while preserving the receipt/tombstone. Application retries never change the approved payload. Once dispatched, release is refused; a delayed original delivery therefore cannot mutate after cancellation. Publication blockage retains fences and uses the existing blocked retry cycle.

## Migration and compatibility

Use the next available additive migration after coordinating current main, never a preselected conflicting number. Preserve all existing receipt, application, fence, task, publication and history records. Historical applications remain discoverable from their saved receipt payload and plan; records lacking sufficient approval evidence expose an explicit recovery limitation. Preflight historical duplicate plan associations and retain each old identity; do not silently collapse or delete them to install a uniqueness constraint.

New-client rollout requires a server capability/version contract. A new client must not claim journal-loss recovery or fall back to the old unreserved apply path when the server lacks it. Define admission for legacy clients explicitly: accepting an old apply can atomically reserve its identity at writer admission and be discoverable afterward, but it retains the pre-admission gap and must be labelled limited. Existing stored journals retain status-first same-ID recovery.

Full PostgreSQL backups must include approval associations/tombstones, saved requests, reserved applications and fences. Restart/recreation and restore must preserve both unused reservations and dispatched applications. The existing migration snapshot export is not a recovery backup for these records. No new startup sweep is needed; existing durable recovery processes dispatched work only.

## Required named regressions for the separate PR

1. `prefix_reservation_lost_acknowledgment_rediscovers_original_approval`: lost acknowledgment plus total journal deletion, reload and delayed first delivery converge to one apply identity.
2. `prefix_journal_loss_before_apply_cannot_allocate_competing_intent`: a committed unused reservation survives deletion; a competing tab finds its scope and cannot create an overlapping logical application.
3. `prefix_journal_loss_after_apply_restores_scope_and_publication_recovery`: dispatched identity/request/scope survive deletion while staging, publishing and blocked; completion is never inferred from delivery acknowledgment.
4. `prefix_concurrent_reservations_return_one_canonical_operation`: real PostgreSQL concurrency for the same approval plus changed-payload and overlapping-scope conflicts.
5. `prefix_discovery_failure_preserves_edit_protection_and_study`: broker/database/API refusal and primary-read authority do not unlock structural controls or block unrelated study.
6. `prefix_reserved_release_serializes_with_delayed_apply`: release wins only before admission; tombstone rejects delayed deliveries, and renewed approval never reuses its cancelled identity.
7. `prefix_reservation_restart_restore_and_replay_preserve_one_effect`: PostgreSQL recreation, backup/restore, stale worker delivery and idempotent replay preserve reserved/dispatched ownership.
8. `prefix_rediscovered_completion_requires_matching_publications`: status must match operation, repertoire, plan, graph/integrity/queue evidence; mismatches and stale approval need actionable recovery.

Register these in `tests/REGRESSIONS.md`. Prove frontend state with deterministic unit/component cases; use real browser reload/storage deletion and real PostgreSQL reservation/concurrency/restore tests at the boundaries. Include foreground contention, bounded work, restart and replay for any new handler. CI owns complete current-candidate qualification; local focused evidence cannot establish merge readiness.
